# WoW Forever DPS & Burst Simulator

See `docs/PLAN.md` for the full project plan and `README.md` for the workspace layout and how to build/run.

## Hard rule: no synthetic placeholder data in any production code path

Decided 2026-10-17, after Phase 1 engine bring-up initially shipped a data pack with synthetic example damage coefficients (tagged `placeholder`) that were never meant to represent real game values. The user's instruction, verbatim intent: **placeholder values must never be reachable by a normal production run.**

This means, going forward:

- **The default/production data pack(s)** loaded by `forever-sim` (and any future web app backend) with no extra flags **must contain only sourced data** — confidence tag `live-confirmed`, `dev-blue-post`, `beta-datamine`, or `community-reported` (Plan Section 3, Principle 2). If a verified value cannot be found for a spell/talent/mechanic, that entry is **omitted from the production pack entirely**, not filled in with a guess. The simulation engine must treat a build that references a missing entry as a hard error ("no production data for spell X"), never a silent fallback to a made-up number.
- **Placeholder values are only permitted inside a dedicated overrides file** (naming convention: `data-packs/overrides.*.json`), clearly and individually tagged `confidence: "placeholder"`, and that file is **never loaded automatically**.
- **Using an overrides file requires an explicit, required command-line argument** at the point the application is launched (e.g. `forever-sim --overrides data-packs/overrides.dev.json`). There is no default path, no auto-discovery, and no environment-variable fallback for this — the person running the simulator must visibly opt in every time. The same requirement applies to any future entry point (web server, worker, test runner) that is capable of running a simulation: if it can load placeholder data, loading it must require an explicit argument/flag at invocation, not a config default.
- When an overrides file is supplied, any result that used an overridden/placeholder value must surface that fact in the output (this follows directly from Plan Section 5's confidence-tag UI treatment — placeholder is just another confidence tier that must never be presented with the authority of real data).

Do not relax this for convenience during development. If a spell's real coefficient isn't known yet, the correct action is: leave it out of the production pack, put a placeholder in the overrides file if you need something to exercise the engine with, and go find the real number (see "Data sourcing" below) before it's needed for a result anyone might act on.

**The same rule applies to gear** (`crates/gear`, added for the Phase 1 "hand-entered gear only" simplification): there is no real, sourced item database in this project — itemizing it is out of scope so far. `data-packs/gear.example.json` exists only to exercise the `--gear` mechanism, every item in it is tagged `confidence: "placeholder"`, and it is never loaded unless `--gear <path>` is passed explicitly, same as `--overrides`.

## Data sourcing

**Revised 2026-10-17 after a real methodology failure was found and fixed.** The original version of this note claimed Wowhead's WoW Forever pages were reliably extractable and tagged `beta-datamine`. That was wrong, demonstrated concretely: fetching a Wowhead spell page through this project's page-fetch-and-summarize tool reliably returns a single flat damage value even when a real min-max range exists (confirmed against a mature, fully-populated live Classic page, not just the Forever beta), and in at least one case (Immolate) returned a value implausibly low by roughly an order of magnitude — a likely outright extraction error, not just a lost range. See `docs/PLAN.md`'s "Wowhead data-sourcing investigation and plan" for the full writeup.

**Update 2026-10-17: found a better source.** `https://thewowdb.com/wow-forever/` is directly accessible (no Cloudflare block like Wowhead) and each spell page explicitly cites "Generated from the SpellEffect, SpellMisc, SpellCooldowns and SpellRange records in the WoW Forever beta client, build 1.60.1.70450" with a consistent, parseable structure. Its `robots.txt` disallows only `/api/` and a few admin-type paths — regular content pages are explicitly welcomed for AI/bot crawling (it names `ClaudeBot`/`anthropic-ai` directly as allowed). **Prefer thewowdb.com over Wowhead for any new spell/talent entry** — fetch it directly (plain `curl`/HTTP works, no bookmarklet needed), and tag the result `beta-datamine`, not `community-reported`, since this is genuine client-data extraction. Re-checking this project's own four Warlock spells against it found the prior revision's WebSearch-synthesized ranges (Shadow Bolt 246-274, Shadowburn 65-74) were themselves wrong — the real values are flat (251, 266), confirmed by a full-text scan finding no range pattern anywhere on any of five spell pages checked, including the user's own Searing Pain test case. Don't assume a range exists just because Classic/other versions have one for the same spell — WoW Forever may have flattened it.

**Update 2026-10-17: the ingestion tool exists now.** `crates/ingest` (`wowforever-ingest` binary) fetches a thewowdb.com spell page and emits a `SpellDef`-shaped JSON object tagged `beta-datamine` automatically — prefer this over any manual curl/research process for anything thewowdb.com covers. Usage: `cargo run -p wowforever-ingest --bin wowforever-ingest -- --spell-id <id> --id <snake_case_id> --name "<Display Name>"`. It fails loudly (non-zero exit) rather than guessing when it can't confidently extract a field.

Current practice for anything thewowdb.com doesn't cover:
- **Never trust a single page-fetch for a numeric value, especially a range.** Run at least two independent web searches (search-engine result synthesis, not a live-page fetch) with an explicit "quote the range, don't average" instruction. This method is more reliable than a single page-fetch but is still not authoritative — when two searches disagree (as happened for Corruption before thewowdb.com resolved it), record the conflict in the `source` field rather than picking a winner.
- **No entry sourced this way may be tagged `beta-datamine`.** That tier is reserved for data that was actually self-extracted from client files (thewowdb.com, or `wago.tools` if that's ever built out). Web-research-synthesized values, however many times cross-checked, are `community-reported` at best.
- `data-packs/forever-beta-2026-10-17-rev2.json`'s per-entry `source` fields, especially the ones marked `CORRECTED` or `UNRESOLVED CONFLICT`, are the worked example of how to cite a correction or an open discrepancy honestly rather than silently.

## Data-pack versioning convention

Decided 2026-10-17 after the gap was found the hard way: the plan calls for "versioned, diffable data packs" (Principle 1) but the actual file-management practice overwrote the same filename (`forever-beta-2026-10-17.json`) in place across three real revisions, leaving no prior version on disk to diff against or recover from. Fixed going forward:

- **Never overwrite a data pack file in place once it has been used for anything** (a test run, a golden value, a historical record). Save each revision as its own file, named after its own `version` field (e.g. `forever-beta-2026-10-17-rev3.json`), and bump the version string for any new revision.
- The two revisions recovered this way (`-rev2.json`, `-rev3.json`) are real — `-rev2.json` was reconstructed faithfully from this project's own prior documentation of its exact contents after the gap was found, not fabricated, but reconstruction from memory/docs is a worse position to be in than just not overwriting the file in the first place. Don't rely on being able to do this twice.
- `crates/cli`'s `DEFAULT_DATA_PACK` constant always points at the current latest revision; update it when publishing a new one.
