# WoW Forever DPS & Burst Simulator — Project Plan (Draft 3)

Status: Draft 3 — revised after independent review and a red-team review. Date: 2026-10-17.

**Engineering status (added 2026-10-17, Phase 1 bring-up underway)**: Section 0.1's primary-source gap is partially closed — [us.forums.blizzard.com/.../2360696/6](https://us.forums.blizzard.com/en/wow/t/wow-forever-beta-development-notes-updated-october-15/2360696/6), posted by Kaivax (Blizzard Community Manager), is a real primary source, and notably does **not** mention Demonic Sacrifice or Demonic Pact — confirming the flagship dispute (2.4) is genuinely still open even against primary data, not just contested secondary sources. The language in this plan has been stack-committed: the engine is being built in Rust (chosen over this plan's earlier Go/TypeScript/Python framing because its WASM output is leaner for Section 5's client-side-compute goal; differential testing against `wowsims/classic` is therefore process-level/black-box rather than shared-code, which is a fine tradeoff). A working Rust workspace now exists (`crates/data`, `crates/engine`, `crates/cli`, `data-packs/`, see `README.md`) implementing: the versioned/confidence-tagged data pack (Principles 1/2), the Demonic Sacrifice × Demonic Pact dispute as an explicit swappable conditional state (Principle 3), the computed DPS delta between its two candidate rules (Principle 13 — e.g. the bring-up data pack's demo build currently shows a +6.4% swing on the unresolved rule), and a populated, open dispute-ledger entry (Section 4.7) with a falsifiable test description. Hand-computed unit tests and golden-file regression tests (Section 0.3) are real and passing; differential testing against `wowsims/classic` (also Section 0.3) is stubbed but **not yet wired up** — see `crates/engine/tests/differential_wowsims.rs`.

**Placeholder-data policy and real sourcing (added 2026-10-17, second update)**: the user set a hard rule, now recorded in `CLAUDE.md`: the production data pack must never contain placeholder/synthetic values, and placeholder data may only reach the engine via an explicit, required `--overrides <path>` CLI argument (no default path, no env-var fallback). Web research starting with the two public sims and specifically including wowhead.com/forever (per the user's instruction) then replaced every placeholder spell coefficient with real, cited `beta-datamine`-confidence data (`data-packs/forever-beta-2026-10-17.json`). That research also materially refined the Demonic Sacrifice × Demonic Pact mechanic itself: two independent sources (wofwforever.com, classicwowforever.com) converge on a more precise rule than this plan's original framing — Demonic Pact exempts summoning a *different* demon from canceling the buff, but resummoning the *same* sacrificed pet still cancels it regardless. The engine, dispute ledger, and candidate rules were all updated to this narrower, better-sourced mechanic; it remains in the open dispute ledger pending primary-source or in-game confirmation, since the Kaivax dev notes still don't mention it.

**Historical Results Storage, Section 4.3 (added 2026-10-17, third update)**: Phase 1's one remaining unimplemented item is now built — `crates/storage` persists every run (full build config + data-pack version) to an append-only, build-fingerprinted store, and surfaces a regression check against the most recent prior run of the *same* build under a *different* data-pack version. Verified end-to-end: running the same build under a simulated patched data pack correctly surfaced a +2.00% DPS delta and both runs appeared in the trend view (`--show-history`). Scoped honestly for Phase 1 CLI bring-up (a local JSON-Lines file, single-writer, not the hosted "Results store" Section 5 envisions for the eventual web app) — see `crates/storage/src/lib.rs`'s module docs for the stated limitation. With this, every named Phase 1 item in Section 7 is implemented: core DPS simulator, versioned data pipeline, historical storage, confidence tagging, and the conditional-mechanic modeling with the corrected (delta-computing) acceptance criterion. Not yet done from Phase 1's own list: actually publishing the data pack as a public, PR-reviewable repository (a hosting/visibility decision for the user, not something to do unilaterally) and the `wowsims/classic` differential-testing leg (still a stub).

**Demonic Sacrifice × Demonic Pact dispute RESOLVED by a primary source (added 2026-10-17, fourth update)**: further research while sourcing data for the burst calculator (below) surfaced an official Blizzard blue post, "World of Warcraft: Forever Class Deep Dives — Rogue and Warlock" (mirrored by Wowhead's Blue Tracker), which confirms word-for-word the exact rule this plan had already adopted as its best-sourced candidate: "Your Demonic Sacrifice effect is no longer cancelled by summoning a different pet. Resummoning the sacrificed pet will still cancel the effect." The data pack's dispute ledger entry is now `status: resolved`, with the contradicted alternative candidate rule kept in the record rather than deleted (Plan Section 4.7's intent: disputes should visibly converge, not vanish). The engine was updated so the live "disputed mechanic" UI warning (`SimOutput::touches_disputed_mechanic`) correctly stops firing once a mechanic's ledger entry is resolved, while the underlying rule-comparison function (`simulate_dispute_delta`) remains available for historical reference — this distinction (mechanically relevant vs. still-live-risk) is now a tested property, not an assumption.

**Burst Damage Rotation Calculator, Section 4.6 (added 2026-10-17, fifth update)**: implemented as its own crate (`crates/burst`), deliberately separate from the steady-state DPS engine per the plan's own framing. Two corrections to the original spec, both load-bearing: (1) the optimization objective is fixed to expected damage only, with the floor (no-crit) figure reported as a stat of that *same* chosen sequence, never a separately floor-optimized one — this directly closes the red-team finding that "maximize EV" and "maximize floor" can disagree on which sequence is best; (2) no Monte Carlo and therefore no common-random-numbers machinery is needed at all — every damage figure in the current data pack has `base_min == base_max`, so expected value and the no-crit floor are both exact closed-form numbers, not samples. The search is a beam search over a GCD-quantized timeline with an explicit, stated beam-width budget, and honestly reports whether its result is provably optimal (the beam never had to prune) or merely best-found-under-budget. Also implemented, per the plan's named specification gaps: an `OpponentProfile` (not just toggles) with per-school resistance, and an `AttackerOpener` with a starting-mana budget that's actually enforced (insufficient mana correctly forces a "pass" rather than an illegal cast, verified by test). `AttackerOpener::opened_from_stealth_or_cc` is recorded but honestly documented as having no mechanical effect for Warlock specifically (no stealth-opener bonus exists for this class) — present for future classes.

Sourcing Shadowburn's real coefficients (Wowhead) for this feature is also what surfaced the Blue Tracker post above. Running the calculator against the real data pack (15s window, full-health opponent) produced a genuinely interesting, correct result worth recording: the optimizer picks Corruption + Shadow Bolt spam over Shadowburn, because Shadowburn's real-game strength is as a low-target-health execute tool (not modeled here) and on a full-health target it's simply lower EV-per-GCD than spamming Shadow Bolt with the current sourced coefficients. This is flagged as a stated limitation (no execute/low-health bonus modeling), not hidden as a success.

**Wowhead data-sourcing investigation and plan (added 2026-10-17, seventh update)**, prompted by the user correctly challenging two things at once: the burst calculator's "no Monte Carlo needed" design (see below), and the deeper question of whether this project's Wowhead sourcing was ever reliable. It wasn't, consistently. This section documents what was actually found, with every claim backed by a real check run during this investigation (not assumed), and the resulting plan.

*What was found.* (1) No official public Wowhead API exists for spell coefficients or damage ranges — third-party documentation confirms Wowhead's own `get_spell`-style lookup returns only id/name/url, nothing numeric. (2) Direct HTTP access to Wowhead is blocked: a plain `curl` request returns an HTTP 403 from Cloudflare/CloudFront bot protection, confirmed directly. (3) The page-fetch-and-summarize tool used throughout this project's earlier research is unreliable specifically at extracting *ranges*: three independent, increasingly explicit attempts (the WoW Forever beta page, a mature live Classic page, and an explicit "look for raw DBC-style fields" prompt) for Searing Pain all returned a single flat number, even though a real range almost certainly exists and the user could see one directly. (4) This wasn't just imprecision — re-checking the project's own already-shipped data found Immolate's sourced value (9 damage at level 60) was implausibly low by roughly an order of magnitude, most likely a genuine extraction error rather than real data. (5) Independent web-search passes (search-engine result synthesis, as opposed to fetching and summarizing the live page) proved more reliable at preserving quoted "X to Y" ranges — Shadow Bolt (246–274) and Shadowburn (65–74) were each confirmed this way, twice, independently. (6) Even that method isn't fully reliable: Corruption's figures disagreed across passes (438 vs. 324 vs. 348 total damage) and referenced two different spell IDs (11672 vs. 172) without resolution — left as an explicitly flagged, unresolved conflict in the data pack rather than arbitrarily picking one. (7) A real structured alternative exists: `wago.tools`, a community-run mirror of Blizzard's own client data files (DB2 tables). Its API (`/api/casc/{fdid}` for raw file bytes, keyed by file ID) was confirmed live and reachable from here — unlike Wowhead, it is not blocked — returning a real, structured JSON error (`{"error":"Invalid FDID"}`) when probed without a valid ID, confirming the endpoint genuinely exists. However, this pattern comes from community tooling READMEs (e.g. `p3lim/dbc-helper`), not an official published contract — `docs.wago.io`, checked directly, documents a *different* product (the Wago Addons distribution platform) and says nothing about DB2 access. Using it for real would mean parsing raw WDC5-format binary tables with column definitions from the separate `WoWDBDefs` project — genuine, nontrivial parser engineering, not a simple JSON fetch.

*The plan, phased:*
- **Phase A (done this turn)**: emergency correction pass on the shipped data pack. Shadow Bolt and Shadowburn's ranges corrected and cross-validated twice each; Immolate's implausible value corrected to a single-source, explicitly-flagged-as-uncertain figure; Corruption left with its original figure but flagged with the exact unresolved conflict found, rather than guessing; every entry's confidence tag relabeled from the prior revision's overclaiming `beta-datamine` to the honest `community-reported`, since none of it was ever actually self-extracted.
- **Phase B (near-term, process only, no new engineering)**: for any future spell/talent entry, require at least two independent WebSearch passes with an explicit "quote the range, don't average" instruction before accepting a value at all; when passes disagree, record the conflict in the `source` field rather than silently picking a winner; periodically re-check entries already in the pack, since this investigation shows already-shipped data can simply be wrong.
- **Phase B+ (done this turn)**: a browser bookmarklet (`tools/wowhead-curation-bookmarklet.js`, install/use in `tools/README.md`) that assists manual curation directly against the real, rendered Wowhead page in the user's own browser — no bot-blocking (it's a real browser session), no AI-summarization lossiness (it reads the actual DOM text). It best-effort pre-fills an editable form (regex pattern matching for damage ranges, SP coefficient, cooldown, cast time, mana cost, and a DoT-component guess) and generates `SpellDef`-shaped JSON for the human to review and export, defaulting `confidence` to `community-reported` (never `beta-datamine` — this is still a human reading a third-party site, not self-extraction). Explicitly surfaces a warning banner when no real "X to Y" range was found and a single value was used instead -- the exact failure mode that corrupted this project's earlier automated extraction, now made visible rather than silent. Verified with a real test harness (`jsdom`, not just eyeballing a real browser): this caught a genuine bug before shipping (`document.body.innerText` returns empty under jsdom, silently zeroing every extracted field, fixed with a `textContent` fallback that also improves robustness in real browsers) and confirmed the no-range warning banner and DoT auto-fill both work correctly against synthetic Shadowburn- and Immolate-shaped page text.
- **Phase C (medium-term, real engineering, not started)**: a small ingestion tool (e.g. a new `wowforever-ingest` crate) that calls `wago.tools`' confirmed-live `/api/casc/{fdid}` endpoint, locates the Spell/SpellEffect/SpellScaling DB2 tables for the relevant build via their file IDs, and parses them with a WDC5 reader using `WoWDBDefs`' published column definitions. This would produce genuinely client-extracted data — `EffectBasePoints`/`EffectDieSides` map directly to this project's `base_min`/`base_max` fields — superseding every web-sourced entry in the pack, and would also be the correct top-precedence source under this plan's own Principle 11 (self-extracted/official client data ranks above third-party guide sites, which is what Wowhead and every community guide used so far actually are). This is a real, scoped engineering investment the user should explicitly sign off on before it's started, similar to the earlier language-choice decision.
- **Phase D (ongoing governance)**: once Phase C exists, re-derive the source-precedence default to literally rank `wago.tools`-extracted entries above web-sourced ones, and schedule re-extraction on new beta/live builds, feeding the existing data-pack versioning and regression-detection machinery (`crates/storage`) automatically rather than manually.

**Burst calculator Monte Carlo redesign (added 2026-10-17, same update)**: the user's challenge also exposed a real, independent bug in `crates/burst`, found while fixing the design: the "floor (no-crit) damage" statistic summed the *same* midpoint-based value used for expected damage, not `base_min` — so it wasn't a floor at all, it was expected damage again, just relabeled. This was masked entirely by the fact that every spell's range was degenerate (`base_min == base_max`) due to the sourcing problem above, so the bug had no visible symptom until real ranges existed. Fixed properly: the search still uses exact closed-form expected value to rank candidate sequences (this part of the original design was correct and unchanged — by linearity of expectation, EV is exact regardless of range width, no sampling needed for ranking); but final reporting of the *chosen* sequence now runs real Monte Carlo sampling (`evaluate_sequence`, new function) to produce an honest `DpsStats` distribution, alongside a correctly-computed `guaranteed_floor` (using `base_min`, explicitly labeled as a theoretical bound, not a realistic outcome — a real 5th-percentile sample is what `monte_carlo.p5` is for). `DpsStats`/`stats_from` were factored out of `crates/engine` into a new shared `crates/stats` crate so both the DPS engine and the burst calculator report distributions the same way. Six tests cover this, including one that specifically asserts `guaranteed_floor < expected_damage` whenever a range is real — the regression test for the exact bug just fixed. Running the corrected calculator against the corrected data pack changed the optimal sequence found (Immolate and Shadowburn now enter the rotation, where the old implausible Immolate value had kept them out) — a concrete demonstration that the data fix, not just the design fix, changes real recommendations.

**thewowdb.com discovered as a materially better source, superseding REV2's corrections (added 2026-10-17, eighth update)**: at the user's direction, explored `https://thewowdb.com/wow-forever/` as a primary data source. This changes the data-sourcing picture significantly, for the better:

- **Directly accessible**, unlike Wowhead — `curl` returns a real 200 with full HTML, no Cloudflare/WAF block. `robots.txt` explicitly disallows only `/api/`, `/admin/`, and a few other paths, but explicitly *allows and welcomes* crawling of its regular content pages — it names `ClaudeBot`/`anthropic-ai` directly, under a comment reading "AI answer-engine crawlers (GEO) - explicitly welcomed so Gemini, ChatGPT, Claude, and Perplexity can read and cite TheWoWDB." No scraping-ethics caution is needed here the way it was for wowforeversim.com/mythicsim.com (Plan 0.2) — reading its pages is exactly what the site asked for. (The disallowed `/api/` path is respected and not used.)
- **Each spell detail page cites its own extraction method directly**: "Generated from the SpellEffect, SpellMisc, SpellCooldowns and SpellRange records in the WoW Forever beta client, build 1.60.1.70450," in a consistent "Effect #N ... Value: X Spell power coefficient: Y" structure across every spell checked. This is genuine client-data extraction, not AI-summarized prose or web-research synthesis — the same category of source as `wago.tools`, but already parsed into clean, directly-parseable HTML, with no WDC5 binary-format engineering required.
- **A genuinely important, unexpected finding**: re-fetching all four of this project's Warlock spells from thewowdb.com, *and* the user's own original example (Searing Pain, spell 17923) specifically to test the premise that "most spells have a range of damage values," found **no die-sides/range field anywhere** — every spell showed a single flat `Value: X`, confirmed by a full-text scan of each page for any "X to Y" or "X-Y" pattern (zero matches). This means REV2's WebSearch-synthesized ranges (Shadow Bolt 246–274, Shadowburn 65–74) were themselves wrong — not just imprecise, but describing a range that doesn't exist for these spells in WoW Forever's redesign. The evidence: internally consistent, explicitly-cited, structured data across 5 independently-checked spells, versus search-engine snippet synthesis that had already been shown unreliable (Corruption's conflicting 438/324/348 figures, Section 4.5's seventh update). This doesn't prove no WoW Forever spell has a range — only that these specific ones don't — but it does mean the original "fix the lack of Monte Carlo" framing was solving a problem that, for this exact data, didn't actually exist; the Monte Carlo/floor-vs-EV engine fix itself remains correct and necessary in general (ranges can exist, and the engine must handle them correctly when they do — covered by synthetic-range tests), it just isn't currently exercised by real variance in this specific data pack.
- **Corrected values now in the pack (REV3)**, confidence raised to `beta-datamine` for every entry (a first for this project — every prior revision was `community-reported` at best): Shadow Bolt 251 (was 246–274), Corruption 73/tick·6·18s/340 mana (was 58/tick·290 mana, itself still unresolved before this), Immolate 158 direct + 55/tick·5·15s/380 mana (was 158 direct + 55/tick, mana cost was wrong at 25 instead of 380), Shadowburn 266 (was 65–74, and before that 67) /365 mana (was 105). The mana costs in particular had never been checked against any source before this pass — all three non-Shadow-Bolt entries were wrong.
- **Revises Phase C of the data-sourcing plan (Section 4.5's seventh update)**: `wago.tools` (raw DB2 binary parsing) is no longer the obvious next engineering investment — `thewowdb.com` already does that parsing and exposes the result as consistently-structured, directly-fetchable HTML, for a game variant that actually matches WoW Forever (unlike `wowsims/classic`, which is a different variant entirely).
- **Data-pack versioning gap found and fixed (added 2026-10-17, tenth update)**: discovered, while planning this recommendation-engine work, that every prior data-pack revision had been *overwritten in place* under the same filename (`forever-beta-2026-10-17.json`) rather than saved as its own versioned file — a direct violation of Principle 1's "versioned, diffable data packs," and it meant there was no real prior revision left on disk to diff against. Fixed: the current pack is now `forever-beta-2026-10-17-rev3.json`; `forever-beta-2026-10-17-rev2.json` was reconstructed faithfully from this plan's own prior documentation of its exact contents (a real recovery, not fabrication, but a worse position to need than just not overwriting the file). `CLAUDE.md` now documents the convention going forward: never overwrite a data pack once it's been used for anything, always save a new revision as its own file.
- **Change-Driven Recommendation Engine, Section 4.4 (added 2026-10-17, eleventh update)**: `crates/recommend` diffs two `DataPack`s field-by-field (damage, coefficient, cast time, cooldown, resource cost, DoT structure, disputed-mechanic status) and cross-references the result against `crates/storage`'s history to find which previously-run builds (by build fingerprint, most recent run only) reference a changed spell — the "builds worth re-testing" list the plan calls for. Deliberately cheap: the diff and the affected-build lookup are pure data comparison, no simulation, consistent with the plan's cost-controls note (screen cheaply first, re-simulate only what's flagged). Re-simulation itself, and recording the result via the existing regression-detection machinery in `RunStore::append`, is wired into the CLI as an opt-in `--resimulate` flag on the new `--mode recommend`, not automatic. Tested against the **real** REV2 → REV3 data-pack diff (not a synthetic fixture) — correctly found all four real spell changes — and verified end-to-end against real (not throwaway-`/tmp`) history: ran the Phase 1 demo build under both real revisions (`history/warlock-demo.jsonl`, committed), then ran `--mode recommend`, which correctly identified the one affected build, correctly excluded Shadowburn (used only by the burst calculator, which isn't persisted to history yet), and `--resimulate` correctly re-ran it and recorded the +2.2 DPS delta. Popularity-weighted prioritization (also named in 4.4) is explicitly not implemented here — it needs real usage telemetry this project doesn't collect yet (the accounts/identity layer, still Phase 2/unbuilt); what's built is the mechanically-affected half of the feature, which stands on its own.
- **Real Arcane Mage rotation: stacking buff, timed burst buff, mana-pool scaling stat, Section 7 (added 2026-10-18, twenty-ninth update)**, after the user judged the Mage demo (Fireball + Frostbolt, 275.7 DPS) "laughably bad" and pointed back at the same mythicsim.com screenshots for direction on what a real spec rotation looks like. Confirmed via `WebFetch` the screenshots are genuinely WoW Forever, Arcane spec. This gap was deeper than the Warrior work (which was mostly data-only once rage existed): the real Arcane kit needs a self-stacking buff (Arcane Blast), a flat timed burst-damage buff (Arcane Power), and a third damage-scaling stat (mana pool, for Arcane Wrath) -- none of which this engine had. Planned and implemented via the same discipline as the Warrior pass (`EnterPlanMode`, real sourcing before code, real tests, real browser verification).
  - **Sourcing found a genuine, dated mechanic rework mid-investigation, not assumed**: an early search described Arcane Blast's stacking window as "8s or reset by casting any other damage spell." A second, more specific search surfaced a named, dated "October 15 2026 beta update" (corroborated by patchbot.io, hotspawn.com, mobalytics.gg) that changed this to a flat 15s window from the *first* stack, **not** reset by other casts -- the newer, dated source was treated as authoritative (same practice as Bloodthirst's Oct-2 AP-ratio change), which also meaningfully *simplified* the engine design (no "reset on other spell" logic needed at all). Arcane Wrath's mana cost and coefficient, and Arcane Blast's base mana cost, weren't independently found after multiple passes -- derived instead from same-cast-time, same-pack sibling spells (Fireball) with the derivation stated explicitly in each entry's `source` field, not silently guessed.
  - **Engine** (`crates/data`, `crates/engine`): new `StackingBuffDef`/`TimedDamageBuffDef` types and `SpellDef.stacking_buff`/`timed_buff`/`mana_coefficient` fields (all `#[serde(default)]`, zero migration). `BuildConfig` gained `max_mana` (deliberately separate from `starting_mana`'s enforcement-toggle semantics -- a stat a formula reads from shouldn't be conflated with whether that resource is gated). `DamageEvent` gained `pct_multiplier`, computed once at schedule-build time (`build_schedule` already has full deterministic knowledge of buff/stack state there) so the RNG-dependent `run_schedule`/`simulate_detail` code only needed one more multiplicative line each. New `current_pct_multiplier`/`effective_resource_cost` pure functions encode the actual rules: a stacking spell never boosts its own damage (the sourced rule is explicit), multiple active buffs compose *multiplicatively* not additively, and the stacking spell's own cost compounds per stack already held.
  - **Deliberately not implemented, with the architectural reason stated plainly**: Missile Barrage and Clearcasting (both true RNG-driven procs deciding, at cast time, whether the next spell is free/boosted) and Presence of Mind (instant-cast conversion). All three would require `build_schedule` -- currently fully deterministic *by design*, so `simulate_dispute_delta` can replay one schedule under two rule candidates with common random numbers -- to become probabilistic. This is the "full APL interpreter" investment `docs/PLAN.md` has repeatedly, deliberately deferred since Phase 1, not a gap specific to Mage.
  - **Verified**: 8 new engine tests, including pure-function tests of the multiplier/cost math and full end-to-end `build_schedule` hand traces proving the exact sourced decay rule (window fixed from first stack, not extended by later casts) and multiplicative composition (`1.69`, not the naive-and-wrong additive `1.60`) -- all passing, plus the full existing suite (84+ tests) unaffected. Real headless-Chrome runs on both `index.html` and `talents.html` confirm identical results and a real multi-ability breakdown (Arcane Missiles, Arcane Blast, Frostbolt all appearing in one representative run).
  - **An honest, lower DPS number, explained rather than hidden**: 199.0, down from 275.7 -- the old number was an artifact of mana being completely unconstrained (the old demo never set `starting_mana` at all, dishonest for a spec whose entire identity is mana management). Debugged directly (temporary instrumentation, since removed) to confirm this is genuine resource contention across five real competing uses, not a bug -- the same honest pattern as the Warrior rage work's 211.6 -> 174.1 correction. **This conclusion was itself wrong -- see the thirtieth update below.**
- **Arcane Mage correction, Section 7 (added 2026-10-18, thirtieth update)**: the twenty-ninth update's "199.0 is genuine resource contention, not a bug" conclusion was challenged by the user, who rejected it outright ("you fundamentally are wrong about the state of the simulation engine... search the web for the fundamental engines other simulators are using and use those results as a new basis") after re-testing and finding the build still only meaningfully used two spells. Re-investigated from scratch against a real reference implementation rather than re-tuning by feel: `mythicsim.com` (the screenshots' source) states it runs "a MythicSim-maintained fork of a third-party ElliotWood/Forever project, built on the open-source `wowsims/classic` engine" -- so `wowsims`' own TBC-era Arcane Blast implementation (`sim/mage/arcane_blast.go`, the closest real analog, since Arcane Blast doesn't exist in vanilla Classic) is a genuine, inspectable ground truth for how Blizzard-shipped stacking-cost abilities actually scale, not just another guess. Fetched and compared directly. Found two real bugs, not one:
  1. **Wrong cost-scaling formula.** `effective_resource_cost` computed `base * own_cost_multiplier_per_stack.powi(stacks)` -- compounding/exponential. `wowsims/tbc`'s real Arcane Blast computes `base * (1 + per_stack_pct * stacks)` -- additive. At the already-sourced 175%-per-stack figure, the exponential version made the 4th stack cost `195 * 2.75^3 ≈ 4055` mana rising to `~11,152` for any further attempt -- against a 6,000 mana pool, i.e. unplayable by construction, not a tuning issue. Fixed to the additive form (`crates/engine/src/lib.rs::effective_resource_cost`, `crates/data/src/lib.rs::StackingBuffDef`'s doc comment); the already-sourced 175% figure itself is unchanged, only the formula shape.
  2. **No "stop rebuilding a maxed buff" condition.** The simplified priority-list rotation model has no way to express a real APL's `buff.stack<max` guard, so Arcane Blast (no cooldown, no DoT) kept winning every GCD it could afford even once already at 4/4 stacks, starving out the spenders (Arcane Missiles/Arcane Wrath) it exists to empower -- confirmed directly: an isolated experiment that only fixed bug 1 (cost formula) actually made DPS *worse* (103.3), because cheap, perpetual Arcane Blast spam out-competed the bigger-hitting spells even harder once it stopped being self-limiting via cost alone. Fixed generically (reads the spell's own already-present `max_stacks` field, not a per-spell special case): `build_schedule`'s rotation-selection loop gained a `stack_ready` eligibility check alongside the existing `dot_ready`/`cd_ready`/`affordable` ones.
  3. **Priority-order bug, found after fixing 1 and 2**: with both bugs fixed, Arcane Wrath (a real 6s-cooldown nuke) still got zero casts in a full 60s run -- it was listed *below* the cooldown-free Arcane Missiles, which (same mechanism as bug 2, one level up) always won the GCD whenever both were affordable, so Wrath's cooldown never got a chance to matter. Reordered to `[arcane_power, arcane_blast, arcane_wrath, arcane_missiles, frostbolt]` -- the same "don't let a short cooldown cap while a repeatable filler keeps winning" principle this project's own Warrior rotation already learned and documented (`try_fire_heroic_strike`'s doc comment).
  4. **Recalibrated the demo build's illustrative mana stats**, the same honest way the melee classes' attack power was already recalibrated (see `CLASS_SIM.hunter`'s note in `web/talent-builds.js`): `starting_mana`/`max_mana` 6,000 -> 10,000, `mana_regen_per_second` 25 -> 40. These are hand-entered build-configuration inputs, not sourced spell data (same category as `spell_power: 350.0`), so this isn't a placeholder-data violation -- the old pair left the build idle for roughly half the fight even after bugs 1-3 were fixed, which doesn't represent a raid-buffed level-60 caster's real mana sustain any more than the melee classes' pre-recalibration attack power did.
  - **Result**: 270.9 DPS (not a straight "higher is better" tuning target -- the point was correctness), with all four real sourced abilities (Arcane Blast, Arcane Wrath, Arcane Missiles, Frostbolt) plus the Arcane Power opener actually appearing in a representative run, instead of one or two spells monopolizing the whole fight. ## 1. Executive Summary

WoW Forever is reported to launch globally 2026-11-04, capped at level 60, with beta running only through 2026-10-21 — meaning **no live level-60 balance data exists yet**, and the two public community simulators (wowforeversim.com, mythicsim.com) are themselves extrapolating from beta datamines. (A red-team pass on this plan found that every one of those dates and facts traces to fan/aggregator sites, not a Blizzard primary source — see Section 0, which is now a blocking gate ahead of everything else.) This plan is for a web application that (a) simulates single-character DPS with the same depth of adjustability as mature tools like SimulationCraft, (b) is explicit about data provenance and confidence so it doesn't silently present beta guesses as fact, (c) can ingest and compare results from the other public sims, (d) stores historical results and reacts to talent/meta changes, and (e) adds a separate PvP burst-damage calculator. Party/raid-wide simulation is scoped as a long-term phase (Section 8).

**Reason to exist, revised after red-team review.** "More adjustable than the incumbents" is a weak differentiator on its own — multi-target/buff-stacking config being undocumented on competitor marketing pages is not proof it's absent, and confidence-tagging is already wowforeversim's own stated practice. The defensible lead differentiator is the **cross-sim comparison and longitudinal patch-history record** (4.2/4.3): both incumbents overwrite their own numbers every patch and don't compare against each other, so a record of "what did build X do across every patch, and how did it compare to the other two sims at each point" is something neither can retroactively produce, however good they get going forward. Everything else in this plan is in service of making that record trustworthy, not of out-simulating anyone on raw feature count.

## 0. Phase-0 Gate: Verification, Legal Clearance, and a Testing Baseline (added after red-team review)

This section exists because the red-team review found the plan's two largest risks were not technical: the project's factual premise is unverified, and its data-sourcing plan carries undisclosed legal exposure. Neither is acceptable to discover mid-build. **No Phase 1 engineering work should start until this gate is cleared.**

**0.1 Primary-source verification.** Every "confirmed" claim in Section 2.1 currently traces to fan/aggregator domains (wowtbc.gg, noobtoboss.com, lfcarry.com, rpgstash.com, wowforever.co/space), not a Blizzard-owned channel — no official announcement, patch note, or press release appears anywhere in this plan's source list for an expansion reportedly 18 days from launch. That absence is itself a finding. Before any product-scope language hard-codes a fact (e.g., "27 trees," "467 talents," a specific launch date), produce a one-page table: claim → primary citation (official Blizzard announcement/patch notes, or direct beta-client observation) → confidence. Anything that fails to find a primary citation is demoted to `community-reported` in the confidence taxonomy (3.2) and removed from scope-defining language — product scope should reference "the current data pack's talent count," never a hard number, for exactly this reason. If the expansion's existence or shape cannot be confirmed from a primary source at all, the fallback scope is a Classic-rules-engine simulator with a pluggable talent dataset, which remains valuable independent of WoW Forever's exact ship date.

**0.2 Legal clearance.** Two distinct exposures must be closed, not just noted: (a) the plan's top-precedence data source (3.11) is self-extraction from a **beta client**, and beta access is typically NDA-gated with EULA language restricting data/reverse-engineering — this must be read and complied with before any extraction happens, and client-side extraction should default to deferred-until-live-client unless the beta terms clearly permit it; (b) the external-sim ingestion feature (4.2) assumed "export formats" exist at wowforeversim.com/mythicsim.com without confirming it — building a scraper against either site risks ToS/goodwill problems with two single-maintainer projects whose cooperation is otherwise the cheapest asset available. Mitigation, sequenced before 4.2 is built: contact both maintainers, ask for permission and (ideally) a sanctioned export endpoint; until/unless granted, ingestion is **user-pasted only** (the user copies their own result in; no crawling of either site). Also confirm the license terms of `wowsims/classic` before any code or data reuse, and keep the project non-commercial while it relies on this kind of tolerated, SimulationCraft-precedent-style data extraction.

**0.3 Testing baseline, available immediately.** The plan otherwise has no correctness-verification strategy until post-launch combat logs exist (Section 6). That gap is avoidable now: `wowsims/classic` is open source and implements overlapping Classic-style mechanics; running this app's engine and `wowsims/classic` against the same shared-mechanic inputs and requiring agreement is a real, live correctness harness that needs no launch and no live logs. Pair this with golden-file regression tests on every data-pack diff (4.5) and hand-computed unit expectations for individual ability damage formulas. This becomes the Phase 1 testing strategy referenced in Section 7.

### 2.2 Mature simulator architecture — the reference model (SimulationCraft)

SimulationCraft is the best available reference for what "accurate and adjustable" looks like in a WoW DPS sim, and several of its architectural choices are directly load-bearing for this plan:

- **Data/engine separation.** Spell, talent, and effect attributes (coefficients, durations, costs, proc chances) are extracted programmatically from the game's own data tables via a tool (`dbc_extract.py`) into versioned, diffable include files, rather than hand-coded into the simulation logic. A build, PTR push, or hotfix triggers a data regeneration and a diff review — not a rewrite of the engine.
- **Action Priority Lists (APLs).** Rotation/cooldown logic is expressed as an ordered list of conditional actions, evaluated at every decision point, using a rich expression grammar (talent-enabled checks, buff/debuff/resource/target-count predicates). This is what makes the rotation *player-adjustable* without touching code — the thing the user specifically asked this app to support.
- **Class modules on shared data.** Spec- (and now hero-talent-) specific behavior is layered as a module on top of the shared spell-data layer.
- **Standard adjustable inputs** across serious sims: gear and stat weights (via iterative scale-factor regression), racials, consumables, raid buffs/debuffs, encounter length, movement/downtime profiles, target count/cleave behavior, and Monte Carlo iteration count — with output reported as a DPS *distribution* (mean, variance, percentiles), not a single number.

### 2.4 Known and discovered simulator accuracy gaps

**General categories** (true of WoW simulators broadly, not WoW-Forever-specific): talents with conditional or resource-*trade* logic (sacrifice/trade mechanics, stance- or form-dependent effects) are the hardest to model and the most commonly approximated or skipped; pet/minion AI is routinely a simplified stand-in for real pet behavior; proc-based talents/trinkets with hidden internal cooldowns or RPPM formulas are mis-modeled until reverse-engineered; tier/item-set bonuses lag at patch launch because they need fresh data extraction; and anything dependent on *player* skill or positioning (movement-interrupted casting, target-swapping, PvP burst timing) is approximated via assumed uptime percentages rather than genuinely simulated, because no generic engine simulates player decision-making.

**Case study — Warlock Demonic Sacrifice.** This is a concrete, present-day instance of the "conditional/trade mechanic gets it wrong" failure mode the user asked to track. Demonic Sacrifice sacrifices the warlock's pet for a long-duration buff (Imp → +15% Shadow damage, Succubus/Incubus → +15% Fire damage, Voidwalker → mana regen, Felhunter → health regen). One community source (wowforever.space) states plainly that "the effect is canceled if any Demon is summoned," making it incompatible with any pet-dependent talent. A second source — the `andycarlson13/foreversims` README — claims a different, newer talent, Demonic Pact, "lifted the old restriction: the sacrificed bonus stays as long as you summon a different demon," directly contradicting the cancel-on-summon rule. **Two sources that both claim authority disagree on whether the buff survives a pet swap.** This is exactly the kind of state-dependent, cancel-on-trigger-unless-you-also-have-talent-Y mechanic that generic simulation engines — built around static buff uptime rather than true conditional state machines — are liable to silently get wrong, approximate, or omit. It is adopted below as the flagship acceptance-test mechanic for the engine's conditional-state modeling (Section 3).

**Community skepticism (Blizzard forums, thread "DPS Sims at Level 60," us.forums.blizzard.com/t/2383077)** reinforces that this isn't a hypothetical concern:
- Sims run on equal baseline gear are, per one poster, "nonsense without gear," since real loot distribution changes relative class performance.
- Sims that ignore secondary effects (e.g., a talent that lowers a core ability's cooldown) are called "worthless" by another poster.
- A third poster notes "other websites have completely different numbers" — i.e., wowforeversim.com and mythicsim.com actively disagree with each other, as already observed in the talent-count discrepancy above.
- A fourth disputes dev-promised rebalancing (rogue capstone talents specifically), implying sims built on pre-balance-pass data are stale before they're even published.
- A fifth, citing Blizzard's own stated plan for roughly six months of weekly post-launch balance passes, concludes that "these sims really mean nothing" right now.

**Calibration methodology.** No Forever sim — including the two reviewed here — currently validates against real combat logs, because no live combat logs exist yet (beta is too new, launch hasn't happened). All current validation is beta-client DB2 extraction or developer datamine comparison. This is a structural, temporary limitation every sim in this space shares today, not a defect unique to any one project — but it means every number any sim produces right now, including this app's, must be presented as provisional until live combat-log calibration becomes possible after 2026-11-04.

### 2.5 Data-update practice — the transferable lesson

SimulationCraft's pattern generalizes directly: separate *data* (versioned, regenerable, diffable spell/talent definitions, ideally machine-extracted) from *engine* (rotation/combat logic that reads that data). A patch then triggers a data regeneration and diff review, not an engine rewrite. Given Blizzard's announced cadence of weekly balance passes for roughly six months post-launch, this separation is not optional polish for this project — it is the only way the app survives its first two months of live service without constant hand-edits to simulation code.

## 3. Design Principles Derived from the Review

1. **Data/engine separation, versioned.** All talent, spell, and gear data live in versioned, diffable data packs tagged to a specific beta build or live patch. The simulation engine reads this data; it never hard-codes spec-specific numbers. This is the single most important structural decision in the plan, and it is what makes "talent trees updatable when Blizzard changes them" (a named requirement) tractable rather than a recurring fire drill.
2. **Confidence tagging on every data point**, mirroring wowforeversim's own "labelled by confidence" practice. Each talent/spell/coefficient record carries a provenance tag (e.g., `beta-datamine`, `dev-blue-post`, `live-confirmed`, `community-disputed`) and the UI surfaces this to the user rather than presenting beta guesses with the same authority as confirmed values.
3. **Conditional mechanics are first-class engine objects, not buff-uptime approximations.** State-trade/sacrifice talents (Demonic Sacrifice is the flagship test case), stance/form-dependent effects, and cancel-on-trigger interactions must be modeled as explicit conditional state, with their governing rule (and, where sources conflict, *both* candidate rules) represented in the data layer and flagged to the user as "disputed mechanic — verify on live" until confirmed. This directly addresses the user's named concern that generic sims silently drop or mis-model talents like this one.
4. **Pet behavior is a configurable-fidelity subsystem**, not folded into generic buff math — simple uptime-approximation mode available for speed, detailed pet-action-list mode available for accuracy, user-selectable.
5. **Explicit proc/ICD/RPPM modeling** as a reusable engine primitive, since this is a named general failure category.
6. **Tier/item-set data ships as its own versioned pack**, decoupled from the base spell data pack, so it can lag without blocking other updates (mirroring the real-world lag SimulationCraft experiences here).
7. **Multi-target/AoE and movement/downtime are explicit, user-adjustable simulation parameters**, not hidden constants — called out because neither public competitor documents this, making it a real differentiator.
8. **Every result is tagged to the data-pack version it was computed under.** A later patch does not silently invalidate historical results — it creates a new data version, and old results remain correctly attributed to the version in effect when they were run. This is what makes historical trend storage and comparison meaningful rather than misleading.
9. **Statistical, not single-number, output.** Monte Carlo iteration with a reported DPS distribution (mean, variance, percentile band), consistent with the SimulationCraft baseline.
10. **External sim results are ingested as labeled, attributed data**, never silently merged with this app's own output — comparisons display source, source-confidence, and talent-data version side by side so disagreements (like the wowforeversim-vs-mythicsim talent-count mismatch) are visible rather than papered over.
11. **Source arbitration is a default with recorded rationale, not a self-serving absolute rule (revised after red-team review).** Ingested external results (4.2) are comparison-only and are never promoted into this app's own internal talent/spell data pack (4.5). The internal data pack's own curation uses self-extracted/official data > developer blue posts > third-party community sims as a *default* ordering — but the red-team review correctly pointed out that "we always rank ourselves highest" is exactly what a skeptical community expects a self-interested new entrant to say. So: the data pack is published as a public, PR-reviewable repository (not a black box); every curated record carries its rationale and an alternative-source note, not just a winning value; disputed or overridden defaults require a named second reviewer; and community-submitted corrections are a first-class input to the pipeline (4.5), not an afterthought — this is also the bus-factor mitigation for a single curator being wrong, slow, or unavailable through ~26 weeks of patch cycles.
12. **Residual limitation, acknowledged rather than quietly "solved" (added after review).** Player-decision-dependent mechanics — movement-interrupted casting, target-swapping, PvP burst timing — are not actually simulated by this app any more than by any generic sim engine (2.4). Principle 7's uptime/movement parameters are a *configuration surface* for the user's own assumptions, not a resolution of the underlying limitation. This is stated explicitly here, and must be stated explicitly in-product (e.g., a visible note wherever movement/positioning assumptions feed a result), so the app does not imply a capability it doesn't have.
13. **Disputed mechanics ship with a default and a measured delta, not just a shrug (added after red-team review).** "We can represent both candidate rules" (Principle 3) is necessary but not sufficient — left there, it relocates the accuracy problem onto the user without resolving anything, which a confidently-wrong competitor can out-compete on trust even while being less honest. Every disputed mechanic (starting with Demonic Sacrifice × Demonic Pact, 2.4) ships with: a chosen default rule and a one-line written rationale for picking it; the alternative exposed as a toggle; the **DPS delta between the two rules computed and surfaced as the headline output** for any build the dispute touches ("this build swings 8% on an unresolved rule"), which is a more useful answer than either bare number; and an owner, a falsifiable in-game test description, and a target resolution date, tracked in a public dispute ledger (4.7) so "disputed" visibly converges toward "resolved" over time instead of becoming a permanent shrug.
14. **Differential and regression testing from day one (added after red-team review).** Correctness cannot wait for post-launch combat logs (Section 6's prior framing). The engine is tested against `wowsims/classic` on shared Classic-style mechanics (divergence is a bug in one of the two engines), against golden-file snapshots on every data-pack diff, and against hand-computed expected values for individual ability formulas. See Section 0.3 and Section 7.

## 4. Product Scope

### 4.1 Core DPS Simulator
In-scope adjustable factors, directly from the task brief and the literature review: class, spec/talent tree selection (against whatever talent set the current data pack defines — deliberately not hard-coded to a specific tree/talent count per Section 0.1's finding that the available counts already disagree with each other), rotation/APL-style spell-priority configuration, gear, racials (including the new Skyborne race and its faction-exclusive fifth class), raid buffs/debuffs and consumables, fight-length and movement/downtime timing, target count (single-target through configurable AoE/cleave), pet behavior fidelity, and proc/ICD/RPPM-governed effects. Output is a DPS distribution with percentile bands, plus the usual scale-factor/stat-weight breakdown.

**Gear input, revised after review**: WoW Forever loot tables are not yet published (mythicsim states this same limitation, 2.3), so an addon-export pipeline has nothing to export against for most of Phase 1. **Manual/synthetic item entry (hand-entered stat blocks against the versioned item-data pack) is the Phase 1 default**, not a fallback; an addon-export/paste flow is added in a later phase once loot tables exist and a companion-addon approach is viable.

### 4.2 Comparison / Ingestion of External Sim Results
A result-ingestion layer that imports external results as attributed records — source, timestamp, source's own talent-data version where discoverable — for side-by-side comparison against this app's own simulation of the same build. This turns the "two sites disagree" problem from 2.4 into a visible, explorable comparison rather than a hidden inconsistency, and is this plan's lead differentiator (Section 1).

**Ingestion method, revised after red-team legal review (0.2).** The original per-site scraping-adapter design is deferred: it assumed export formats exist at wowforeversim.com/mythicsim.com without confirming it, and building a scraper against either site risks ToS and goodwill problems with the two single-maintainer projects whose cooperation is the cheapest path to the same data. Default mode is **user-pasted ingestion** — the user copies their own result from either site into this app. A sanctioned adapter against a maintainer-provided export endpoint is pursued in parallel (0.2) and promoted to automatic ingestion only once permission and a stable endpoint exist.

### 4.3 Historical Results Storage & Trend Analysis
Every simulation run (user-initiated or ingested) is persisted with its full input configuration and the data-pack version it ran under. This supports trend views (how did this build's DPS move across patches), regression detection (did a hotfix quietly nerf a build), and the comparison feature in 4.2.

### 4.4 Change-Driven Suggestion / Recommendation Engine
When a new talent/spell data version is published, the system diffs it against the prior version to identify which specs/builds are mechanically affected, and surfaces a "builds worth re-testing" list. Separately, it tracks which specs/builds users are actually simulating (a popularity signal) to prioritize validation effort and surface trending builds — both named requirements from the brief ("class changes," "increased popularity of builds," "other emerging factors").

**Cost controls, added after red-team review.** This feature's value scales with how aggressively it re-simulates, which makes compute cost the hidden price of the differentiator, peaking on patch weeks exactly when traffic also peaks. Concretely: affected builds are screened with a low-iteration pass first, with full-iteration runs only on demand or for the highest-popularity builds; a stated monthly compute ceiling gates total re-simulation volume with a defined degradation mode (screening-only) if exceeded; and, as a structural cost reducer, the core simulation engine is designed to run client-side (a WASM-compiled build, matching the approach `wowsims/classic` already takes) so the marginal cost of a user-initiated run is the user's own device, not this app's server budget — server-side compute is reserved for the recommendation engine's own background screening, not for every user click.

**Popularity-signal circularity, added after red-team review.** Using simulation popularity to direct validation effort, which then improves quality for already-popular builds, risks locking in whatever the launch-week meta happened to guess first. Mitigation: cap the popularity signal's influence weight, seed initial priority from an external meta source (e.g., build guides, not just in-app usage) rather than from a cold-start popularity count of zero, and keep a manual override so a build that's underrepresented in usage but mechanically interesting (e.g., it touches a disputed mechanic, 4.7) isn't starved of validation attention.

### 4.5 Talent Tree Data Pipeline
A versioned, diffable talent/spell data pack per the SimulationCraft-derived pattern in 2.5/3.1, with confidence tagging (3.2) and a defined update workflow: new Blizzard build or patch → data pack regenerated/hand-curated → diffed against prior version → reviewed → published as a new tagged version → change-detection (4.4) fires against it. This is the mechanism that keeps the simulator from going stale through the announced ~6 months of weekly post-launch balance passes.

### 4.6 Burst Damage Rotation Calculator (PvP)
A distinct simulation mode, separate from the steady-state DPS engine, answering a different question: the maximum damage a character can land in a short, fixed window (on the order of a few seconds up to roughly 15 seconds) by stacking cooldowns/burst abilities, rather than steady-state rotation DPS over a long encounter. Distinguishing design needs: a short fixed time horizon instead of Monte Carlo steady-state iteration; configurable pre-buff/pre-pot assumptions (burst calculated with vs. without pre-cast buffs); opponent-side mitigation toggles (target armor, resistances, PvP-specific damage reduction, trinket/CC-breaks) since the target is a player character, not a raid boss; and output framed as "maximum achievable damage in N seconds under configuration X" rather than a DPS distribution, since burst windows are closer to deterministic cooldown-sequencing problems than long-run averages. This mode should visibly reuse the same underlying talent/spell/gear data pack as the core simulator (3.1) so a talent-data update updates burst calculations too, without a separate data pipeline.

**Specification gaps closed after review**, needed before this is buildable:
- **Opponent profile, not just toggles.** The target needs a defined baseline PvP character profile (class/spec/gear tier/resilience-equivalent stat, not just loose armor/resist sliders) so results are reproducible and comparable across runs, not just abstract "damage into a wall."
- **Attacker-side opener state.** The window's starting conditions must specify whether the burst is opened from stealth/a CC chain (stunlock-style openers) and the attacker's starting resource state (energy/mana/rage/combo points/runes-equivalent) at t=0 — both materially change which cooldown sequence is even legal, not just optimal.
- **RNG inside a "deterministic" window.** Proc-based abilities (crit, proc-triggered effects) still have randomness even in a short window; this mode reports either a worst-case/guaranteed-floor number, an expected-value number assuming average proc luck, or both — it does not silently assume every proc lands, which would contradict the proc-modeling principle (3.5) used elsewhere in the app.
- **Optimization, not just evaluation — with a fixed objective (corrected after red-team review).** The original spec left the optimization objective ambiguous: maximizing expected damage, maximizing the 5th-percentile floor, and maximizing the guaranteed-minimum floor are three different objectives that can select three different sequences (a proc-gambling sequence can win on expected value while losing on floor), so "report the optimal sequence's floor or expected value or both" was not actually well-defined. **The primary objective is fixed as expected damage**; the floor/worst-case figure is reported as a secondary statistic *of that same expected-value-optimal sequence*, not as the result of a separately-optimized floor-maximizing search. Search is implemented as beam search or branch-and-bound over a GCD-quantized timeline with dominance pruning — not exhaustive permutation, which becomes intractable as cooldowns/talents are added — under an explicit, stated search budget; output is labeled "best sequence found under budget B," never "optimal," and the search heuristic is validated against brute-force exhaustive search on a small ability subset to quantify how far it falls short. To keep repeated runs comparable (so "optimal" doesn't just mean "got lucky"), candidate sequences are compared using **common random numbers** — the same proc-RNG stream reused across candidates within one search — rather than independent random draws per candidate.

### 4.7 Dispute Resolution Pipeline (added after red-team review)
A public ledger of every `community-disputed` data point (3.2), each with: the two (or more) candidate rules and their sources; the default currently in effect and why (Principle 11); the computed DPS delta for any build the dispute touches (Principle 13); an assigned owner; a falsifiable in-game test description (e.g., "cast Demonic Sacrifice, summon a different demon, observe whether the buff persists"); and a target resolution date. This is what makes "disputed" a visibly-converging state rather than a permanent shrug, and it is the concrete mechanism behind Principle 13.

## 5. System Architecture (conceptual)

- **Data layer**: versioned talent/spell/item/racial data packs, each tagged to a build/patch, each record confidence-tagged (3.2), diffable between versions, curated per the source-arbitration precedence (3.11).
- **Simulation engine**: reads the data layer; two modes — steady-state Monte Carlo DPS (4.1) and short-horizon burst calculation (4.6) — sharing the same conditional-state modeling for talents (3.3) and the same proc/pet subsystems (3.4/3.5). **Buff/debuff state is modeled from the outset as a shared namespace keyed by character, not a single-character global** — a single character is simply the N=1 case. This is pulled forward from Section 8 on review: the raid-simulation phase must not be the first time this constraint is applied, or it risks the retrofit Section 8 itself warns against.
- **Ingestion/comparison layer**: per-external-source adapters (4.2) normalizing third-party results into the same attributed-result schema used internally; ingested data is comparison-only and never writes into the internal data layer (3.11).
- **Results store**: every run persisted with full input config + data-pack version (3.8/4.3), queryable for trend/regression analysis and for the recommendation engine (4.4).
- **Change-detection/recommendation service**: diffs successive data-pack versions and cross-references usage/popularity telemetry (4.4). Re-simulating every potentially-affected build/gear/race combination on each data update is combinatorially large (comparable prior art runs thousands of iterations across dozens of builds and 100+ race combinations) — this service runs as a queued, budgeted background job, not a synchronous request, with caching of unaffected results between data versions.
- **Accounts/identity layer (added after review; privacy note added after red-team review)**: historical storage (4.3) and popularity telemetry (4.4) both imply persistent identity across sessions; the app needs at least lightweight accounts or stable anonymous session identity to attribute saved results and usage signal. Any account/telemetry data that is personally identifiable triggers standard privacy obligations (e.g., GDPR-style data-subject rights) that must be designed in from the start (data retention policy, export/delete-my-data path) rather than retrofitted once accounts exist.
- **Confidence-tag UI treatment (added after review)**: Principle 2's confidence tags are a core trust mechanism, not metadata — results views must visibly color-code or badge confidence level, allow filtering to e.g. "live-confirmed only," and surface an explicit warning when a result depends on a `community-disputed` data point (such as either candidate Demonic Sacrifice rule, 2.4).
- **Client-side simulation compute (added after red-team review)**: the core simulation engine compiles to run client-side (e.g., WASM, mirroring `wowsims/classic`'s own approach) so that user-initiated simulation runs cost this app's server budget nothing marginal; server-side compute is reserved for the recommendation engine's background re-simulation (4.4), which has its own stated cost ceiling.
- **Data-pack repository (added after red-team review)**: the versioned talent/spell/item data pack (first bullet above) is published as a public, PR-reviewable repository, not an internal black box — this is the concrete mechanism behind Principle 11's governance fix and gives external contributors, auditors, and skeptical community members a way to see and challenge curation decisions directly.
- **Frontend**: build configuration (class/spec/talents/gear/rotation/buffs/timing/targets), results/trend dashboards, comparison views, the dispute ledger (4.7), and the separate burst-calculator UI.

## 6. Open Questions / Risks, with Mitigations (revised after review and red-team review)

- **Calibration tolerance was never actually specified.** "±X%" in the prior draft left X undefined, which means `live-confirmed` could never be awarded non-arbitrarily. Mitigation: calibrate against **self-generated, controlled logs on a scripted rotation** (not raw aggregate player logs, which confound player skill with engine error), with per-ability tolerances written into the plan once a live client exists, not just a single aggregate percentage.
- **Patch-cadence load on the data pipeline, and the rehearsal mitigation is itself calendar-fragile.** Blizzard's pending ~6 months of weekly balance passes means the data pipeline (4.5) will be exercised almost immediately and repeatedly. The prior mitigation — dry-run the pipeline against a real beta build change in the ~4 remaining beta days — depends on a beta build actually landing in that window, which this plan cannot control; if none lands, the mitigation silently fails to trigger. Revised mitigation: make the rehearsal **event-triggered** (fires on the next beta build push, whenever that is, not tied to a specific date) and build a fallback that needs no external event — a synthetic rehearsal by hand-editing a copy of the current data pack and running it through the full regen → diff → review → publish cycle.
- **Source disagreement now has a policy, not just a flag — and the policy itself needed a governance fix.** The original fixed precedence rule (self-extracted/official > dev blue posts > third-party sims) was flagged by red-team review as self-serving on its face — "we always rank ourselves highest" reads as "trust us" to a skeptical community. Resolved via Principle 11's revision: precedence is a default with recorded rationale, published in a public PR-reviewable repository with second-reviewer sign-off on overrides, not an unchallengeable internal rule.
- **Gear/loot tables not yet published.** Resolved via 4.1's revised Phase 1 default of manual/synthetic item entry rather than treating addon-export as the baseline.
- **Adapter brittleness and legal exposure in external-sim ingestion.** Scrapers against two actively-changing, single-maintainer sites would break roughly weekly even before considering ToS risk. Resolved via 0.2/4.2's revision to user-pasted ingestion by default, with a sanctioned adapter pursued only with maintainer permission.
- **No primary source for the project's own premise.** Resolved via the Section 0.1 verification gate — this is now a blocking Phase-0 task, not a residual risk left for later.

## 8. Party & Raid Simulation

Originally scoped as long-term/not-detailed-here. A real first slice now exists (added 2026-10-17, see docs' engineering-status log below): `crates/raid` computes aggregate raid DPS by independently simulating each member and aggregating their output the statistically correct way -- summing each member's *same-iteration* Monte Carlo sample before taking percentiles of the sum, not summing each member's independently-computed percentiles (which would be wrong, since percentiles of a sum aren't the sum of percentiles even though means are). Verified concretely: a toy 2-person raid's reported total stdev matched `sqrt(stdev_a^2 + stdev_b^2)` (independent-variance aggregation) rather than `stdev_a + stdev_b` (what naive/incorrect aggregation would give), confirming the implementation is actually doing the statistically correct thing, not just producing plausible-looking numbers.

What this first slice explicitly does **not** do, by design, not oversight: model shared raid buffs/debuffs with caps, debuff-limit interactions, or synergy effects between group members (each character is simulated as if soloing -- only the *output* is aggregated, not the simulation itself). Section 5's architectural guidance -- "the engine's shared-state model for buffs/debuffs should be designed from the start to extend from one character to N characters sharing a buff/debuff namespace" -- is still aspirational for the *simulation* layer itself; what's built now is aggregation of N independent single-character simulations, a different and smaller thing than true co-simulation.

The healing-throughput model's healer-output half is now real (added 2026-10-17, see `crates/heal` and the engineering-status log below) -- Priest (Renew, Flash Heal), real sourced data, real HPS simulation. The "vs. a simulated incoming raid-damage profile" half remains unbuilt: that needs an encounter/boss-damage model this project has no honest basis for yet (no launched content to source it from), so it's left unbuilt rather than faked.
